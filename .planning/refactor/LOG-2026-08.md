### Every checker was made to fail before it was believed

This is the part worth carrying forward. Each of the four was green on the whole tree at some
point *while being incapable of failing*, and only a deliberate control found it.

**`check-surface.py` — my control was wrong twice before the checker was.** Rewording
`"Remote pick banner: "` changed nothing, because the token rule is deliberately two-or-more
SHOUTED words; including sentence-case strings would make every string edit a failure. Renaming
`"VOICE SPATIAL up"` changed nothing either, because `VOICE SPATIAL` still existed at three other
sites and was therefore still greppable. The checker was right both times. Only renaming a
**unique** marker — `ACTION DID NOT COMMIT` in `UiSoundEar` — failed the gate.

It also could not see anything at all from a foreign working directory: `SRC` was the relative
string `"src"`, so `os.walk` found nothing and an empty census diffs clean against an empty
census. Resolved from `__file__` now.

**`check-partial-order.py` — four defects, all found by a synthetic two-part type.**

1. `(?P<mods>(?:static|readonly|…)\s+)+` repeats the *named* group, and Python keeps only the last
   repetition. `internal static readonly int Seed` yielded `mods='readonly '`, so **every
   `static readonly` field in the mod was invisible**. It passed the entire tree while being
   structurally unable to fail.
2. `=(?!=)` matched every expression-bodied member. Seven fired; all seven were false, because
   `static bool Foo => _bar;` is evaluated on each *read*.
3. A cross-part **method call** is not a dependency — methods have no initialisation order. The
   first genuine hit was `VROptionsTab::DependencyParents <- ::Id`, and `Id` is
   `section + "/" + key`. The traversal follows methods and reports only fields.
4. A one-line type body was invisible to the line-based walker — the type did not even register
   as having a part. Found because a one-line probe reported clean and *the probe was the bug*.
   Now refused outright.

**`check-instrument-writes.py` — 197 → 84 → 66, and the two narrowings are the tool.** Fixing
what counts as a *read* (assignment targets anywhere in a `=` chain are writes, not reads) took
197 → 84. Fixing what counts as a *diagnostic* took 84 → 66: the name pattern is only a seed, and
a method is promoted when all of its callers are already instruments, to a fixpoint. 294 seeded +
112 promoted = 406 of 4 358 methods.

**`check-frame-order.sh` — verified by swapping two calls** the new marker orders; exit 1, both
lists printed side by side.

### And one false positive that would have poisoned every remaining guard run

The first `check` after committing 1.1/1.3 reported `CHANGED BuildInfo.cs` with `git diff -- src/`
empty. The commit mask is `\b[0-9a-f]{9,40}\b` — nine or more — and `BuildInfo.Commit` carries
git's **seven-character** short hash. The guard was going to show one red line after every commit
of this refactor: the same defect class as the `-dirty` suffix and the `[branch]` token that
`LOG.md` already recorded, and the same reason it matters.

Lowering the generic threshold to 7 would start masking ordinary hex words, so the two revisions
that can actually appear — the baseline's recorded rev and current `HEAD` — are masked **by
value**, longest prefix first. Verified across a real commit boundary.

### What Phase 1 hands to the later phases

- **A 66-entry work list** (`INSTRUMENT-WRITES.baseline`) that is Phase 5's actual scope, with the
  shape of the problem visible in it: `FadeDriver::_walkEdgePending` is written by
  `LogWalkInsideEdge` and read in `Tick()` as `if (_walkEdgePending)`. 33 of the 66 sit in
  `FadeDriver`.
- **A proof that compile order is currently irrelevant** across all 20 multi-part types, so parts
  may be renamed and split freely — and a checker that keeps it that way.
- **A gate that fails on a removed config key or grep token**, which is what turns retiring an
  instrument from an accident into a listed act.

### Corrections to the plan

- The plan said the frame-order audit would "expect a small number" of new entries. It found
  **81 unmarked methods with four or more steps in new files** and locked **two** — because the

  refused and why.
- The plan quoted **197** possibly-load-bearing fields as an upper bound. The real figure under a
  correct definition of "read" and a call-graph-derived instrument set is **66**.

## Phase 1b — folder restructure · **complete** (user request, 2026-08-26)

Not in the original plan. The user asked whether reorganising the folders was worth it, because
a module had become a folder nobody could scan. It was, and it turned out to be the safest
operation in the whole programme — but only because Phase 1 had just landed.

| module | files at the folder root | subfolders |
|---|---|---|
| `WorldUI/` | 101 → **12** | 10 |
| `Core/` | 91 → **17** | 11 |
| `Net/` | 65 → **14** | 3 |
| `Cards/` | 51 → **14** | 5 |

**251 files moved, 0 changed in the compiled form.** Max files in any one folder: 101 → 37, and
that 37 is `Net/Remote` — one prefix, one job. Median folder is 8.

### Namespaces were NOT changed, and that was the whole design

A namespace rename renames every type in the folder, so the guard would report hundreds of
NEW/GONE entries in exactly the commit where *prove nothing else moved* is the point. C# does not
require the two to agree, and this repo already diverged in two places. `using` statements and
every existing reference are untouched. `.editorconfig` now silences IDE0130 so an IDE stops
offering to "fix" it, and `docs/DEVELOPING.md` says why.

### Phase 1.1 is what made it safe, which was not the reason it was written

Moving a file changes MSBuild's glob order, which reorders static field initialisers across the
parts of a partial type — the defect that once swapped two statics in `CanvasConversion`'s field
table. `check-partial-order.py` had just proved that no initialiser in the mod depends on another
part, so the reshuffle cannot matter. The worst case was moved first on purpose: the 15-part
`WallSegmentFade` family, guard empty.

### Five path couplings, every one loud — and two of them better than anything Phase 1 added

Nothing was discovered silently, which is the entire reason a 251-file move is routine here.

| pin | how it announced itself |
|---|---|
| `FRAME-ORDER.lock` file column | named the marker and both paths |
| wire-test `.csproj` explicit sources | `CS2001` naming each missing file |
| ~30 pins in `check-mirrors.sh` | "did it move or get renamed?" |
| `check-remote-defaults.py`, `check-wire-coverage.py` | `FileNotFoundError` with the path |
| `docs/PATCH-INVENTORY.md` | generated; `check` refused until regenerated |

And two wire tests do not merely pin a path, they check that they can still **find** what they
lint: `WaterOwnSurfaceVectors` counts the water sources it sees — *"A sudden drop means this lint
stopped looking at the driver"* — and `Shims.cs` pins `HeadMaskLibrary.cs` because the shimmed
`MaskCount = 3` is otherwise unverified. Both fired, both were right. That is exactly the
self-checking shape Phase 1 had to retrofit four times, and it was already here.

### One `MOVED` that is not a failure, and it took proving

R1 says `MOVED` is a failure, because a reordered field initialiser looks exactly like a clean
move. Every restructure commit reports `MOVED GloomhavenVR.csproj` — which is **synthesised by
ilspycmd** from the AssemblyRef metadata table, whose order follows the order in which the
compiler first touched each reference, i.e. compile order. Verified rather than waved away: six
differing lines, one `<Reference>` block, the two files identical as multisets, and no other file
in the snapshot differing at all. An added or removed reference classifies `CHANGED`, so the
distinction still holds. Written into the guard beside `classify()`.
