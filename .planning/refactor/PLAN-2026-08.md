## 1. Rules for this refactor

Everything in `CHARTER.md` §2–§6 stands. Three rules are tightened or added.

**R1 — The pass condition is an EMPTY guard diff for motion, never `MOVED`.**
`LOG.md` records why, and it cost a near-regression: field initialisers run in declaration
order, and across partials that order follows *compile* order, so a reordered initialiser also
classifies as `MOVED`. `CanvasConversion`'s field table came back with `LastMaskExclusions` and
`DiagSb` swapped, under a rule that accepted it. **`MOVED` is a failure. Reset and redo.**

**R2 — The predicted diff is written into the commit message BEFORE the check is run.**
Not after. A prediction written after the fact is a description. Any type in the actual diff
that is not in the prediction stops the batch.

**R3 — One refactor operation per commit.** A file split and a rename in one commit produce a
diff nobody can attribute. This is slower and it is the whole point of "lieber brauchst du
länger als Regressionen einzubauen".

**Tiers** (from `CHARTER.md` §4, restated only as a reminder of what stops):
- **Tier 0** — provably compiled-form-free: comments, local renames, `!` suppressions, file
  moves, doc updates. Guard must be **empty**.
- **Tier 1** — motion: file splits, member extraction, type moves. Guard **empty** for pure
  motion; confined to the predicted type for extraction.
- **Tier 2** — structural: layering, de-duplication, instrument policy. Behaviour argued in
  writing, guard diff predicted and confined.
- **Tier 3** — behaviour. **Out of scope.** Routed to the user with the evidence, never taken.

**The standing project rulings are not suspended by a refactor.** Doorway segments never fade.
Lights are never written. Figures are never touched. The crystal formation stays. There must
never be empty windows. It must always be possible to open the options menu. Everything stays
multiplayer-compatible. `ressources/`, `libs/` and `decompiled/` are read-only.

## 2. The work, in order

The order is not arbitrary: each phase builds the instrument the next phase needs. Phases 1
and 2 change no code at all, and they are where the regressions get prevented.

### Phase 1 — Grow the apparatus to fit the tree (no source changes)

Pure additions. Nothing here can break the mod, and everything after it is safer because of it.

**1.1 A checker for the partial-part compile order.** Enforce, for every multi-part type, that
either the parts are digit-prefixed **or** no static field initialiser in any part reads a
static member of another part. Fails on a new part that breaks the property. This closes the
`LOG.md` trap permanently instead of relying on a convention six families already do not follow.

**1.2 A checker for instrument/mechanism separation.** For every method whose name marks it as a
diagnostic, report any field it writes that is read outside a diagnostic. Ships **as a report
with an accepted baseline**, not as a hard fail — the load-bearing writes are real code that
exists today and must not be broken to satisfy a linter. The baseline shrinks as Phase 5 works
through it, and the checker hard-fails on anything **new**.

**1.3 Wire `check-surface.py` into `refactor-guard.sh check`.** It already exists and already
does the right thing; it is simply not in the gate. Snapshot at the start of each batch, diff at
the end. This is what makes a removed log token or config key impossible to do by accident.

**1.4 Re-audit the frame-order lock across the 311 new files.** Not "lock everything" — apply the
lock's own stated test: does the ordering span more than one method, or is it non-obvious at the
site? Add entries only where it does. Expect a small number; record the ones deliberately *not*
locked and why, in the lock file, as it already does.

**Deliverable:** four checkers green, baselines recorded, zero source lines changed.

### Phase 5 — Tier 2: the instrument policy

The largest mass (§0.3) and the one that needs a policy rather than a purge.

The measured starting point: **295 fields are written inside diagnostic-named methods**, and the
first-pass classifier puts an upper bound of **197** on how many are read from outside a
diagnostic.

> **That 197 is an upper bound and is known to over-report.** Calibrating it against two sites
> found two systematic false positives, both mine: a chained reset `_a = _b = _c = 0;` counts
> `_b` and `_c` as *reads* because only the first name is at the start of the line, and a reset
> helper named `ResetReport` does not match the diagnostic name pattern, so its writes count as
> outside reads. Over-reporting is the correct direction — a false "load-bearing" costs a read,
> a false "safe" costs a regression — but the number is a **reading list, not a finding**.
> Classifying it is the first task of this phase.

Then, per instrument, exactly one of four outcomes:

1. **Self-contained and still useful** → gate it behind its existing config flag, prove the gate
   costs nothing when off, leave it.
2. **Self-contained and spent** (its defect is fixed and its build note says so) → retire it.
   `check-surface.py` will name every log token it removes; each goes in the commit message.
3. **Load-bearing** → separate the write from the report. The write moves to the mechanism, the
   report reads it. This is the change that makes outcome 2 possible *later* and is the direct
   fix for the class that nearly latched the wall fade off.
4. **Load-bearing and inseparable** → rename it so its name stops lying (`Log…` → the thing it
   actually does) and record it in the registry.

Also here: the **8 duplication groups** (§0.2), each read before touched, with the mirror pairs
expected to end as "deliberate, documented, not merged"; and the **WorldUI ↔ Cards cycle** plus
**`Defaults` → `WorldUI`**, where the fix is moving the shared types (`ButtonTuning`,
`NativeButtonSkin`, `PanelGrabHandle`) to whichever side owns them, not adding an interface.

## 3. Execution shape

Phases 1 and 2 are sequential and mine. Phases 3–5 split cleanly by **file ownership** —
WorldUI / Core / Net+Rig / Cards+Board+Hands — which is how the first refactor ran four workers
without a single merge conflict, on isolated worktrees, each starting from
`git fetch origin && git reset --hard origin/dev`, none of them committing to `dev`, pushing, or
bumping `ModBuild`.

Two hazards recorded from experience: **never `git stash`** (`refs/stash` is shared across all
worktrees) and **worktrees branch from `origin/main`** — a stale-base patch reverts parallel
lanes, so every worker is restricted to its owned paths.

## 4. What this refactor will not do

- Touch tuning values, frame timing, the wire format, Harmony patch targets, or anything the
  user would have to re-test on hardware.
- Merge a local↔remote mirror pair.
- Delete a diagnostic whose write is load-bearing.
- Re-cut a type that is already split into readable parts.
- Change a log token or a config key by accident. Both are guarded; either is a deliberate,
  listed act or it does not happen.
- Resolve a Tier 3 finding. Those are written up with evidence and handed over.
