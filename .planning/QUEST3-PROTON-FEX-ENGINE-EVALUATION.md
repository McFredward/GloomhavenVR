# Quest procedural engine: Android ARM64EC Wine/Proton with FEX

Status: source evaluation only, 2026-10-06. No backend, APK, builder, game input, or protocol was changed for this evaluation. Guildmaster is included again following the maintainer's latest instruction; Workshop remains excluded. B625's corrected Box64 backend remains the implementation under test.

## Assessment

A bounded Android ARM64EC Wine/FEX experiment is justified. There is an actual Android Bionic build of GameNative's Proton Wine, and FEX supports CPU translation inside ARM64EC Wine. That architecture can keep Wine's Unix implementation and Windows system libraries native ARM64 while translating the original x64 procedural engine and our small x64 worker. It eliminates the requirement to translate an entire x64 Linux Wine process and carry its x64 Unix dependency tree. This is an architectural opportunity, not evidence of lower Quest loading time, memory use, or VR frame cost.

Proton includes Wine; replacing Wine with Proton does not remove Windows compatibility code. For this headless worker, the useful component is an Android-adapted ARM64 Wine loader/server with ARM64EC libraries and FEX, not Proton's complete Steam launcher or desktop graphics stack. Valve documents Windows x86 execution on Steam Frame through Proton/FEX and Android execution through Lepton. Steam Frame's Linux runtime is not a drop-in Quest Android runtime. [Valve compatibility documentation](https://partner.steamgames.com/doc/steamhardware/steamframe/compatibility)

The Windows FEX modules perform CPU emulation while Wine and the ARM64EC ABI handle system calls and transitions. FEX's Linux application emulator is explicitly unsupported on Android; its reusable CPU core is a separate case. The ARM64EC development page is the more specific authority for today's Windows-module behavior; an older FAQ's restriction on Windows DLL use must not be treated as a current blanket ARM64EC verdict. Neither page establishes compatibility with Quest's application sandbox. [FEX ARM64EC documentation](https://wiki.fex-emu.com/index.php/Development:ARM64EC), [FEX FAQ](https://wiki.fex-emu.com/index.php/FAQ)

## Preserve the existing boundary

The experiment should retain the original `ApparanceWorker.exe` as x64 PE and the owner's original `ApparanceEngine.dll`. The current Android bridge exposes all twelve original functions, sends copied buffers over one local socketpair and keeps guest pointers inside the worker. The little-endian protocol stays version 1 with its twenty-byte header and 128 MiB maximum payload. No translated engine pointer or callback address should enter Unity's ARM64 address space. [Current bridge contract](../tools/quest-procedural-runtime/README.md), [worker](../tools/quest-procedural-runtime/worker.c), [protocol](../tools/quest-procedural-runtime/protocol.h)

Keeping both the worker and engine x64 preserves their direct function-call and log-callback ABI. Calls to Wine's ARM64EC system libraries still need the supplied Wine/FEX transition machinery. New synthesis threads, TLS, exception unwinding and reentrant callbacks remain meaningful tests, even with an unchanged worker. The original `ApparanceUpdate` also passes a three-float struct by value; this must remain covered by the existing oracle.

A native ARM64EC worker is a later, optional optimization. It would need an ARM64EC compiler and verified entry/exit thunks, indirect `GetProcAddress` calls, mixed-mode exception handling and callback transitions from an x64 engine. Compiling a plain AArch64 Windows executable or calling the engine directly from the Android bridge does not supply those contracts. FEX's ARM64EC source contains its own indirect-call handling and per-thread state; native UnixLib dispatcher calls even use a dedicated trampoline to avoid ordinary ARM64EC call dispatch. [ARM64EC implementation](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/Source/Windows/ARM64EC/Module.cpp), [UnixLib dispatch and fallbacks](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/Source/Windows/Common/FEXUnixLib.cpp)

## Smallest justified runtime candidate

The checked owner DLL is x64, SHA-256 `03cd691469b2169e701982098e16729dbca7398c3c2637d6377ebabf52302260`. Actual `llvm-readobj --coff-imports` inspection found these direct dependency groups:

| Group | Required capability |
| --- | --- |
| `KERNEL32`, with its transitive `KERNELBASE`/`ntdll` | Threads, TLS, events, mutexes, file IO, virtual memory, context/unwind functions, and process/pipe APIs. |
| `MSVCP140`, `VCRUNTIME140`, nine `api-ms-win-crt-*` imports | C++ threads/condition variables, locale, exceptions, heap, IO, strings, conversion, math, time and filesystem. Resolve the resulting UCRT/API-set closure. |
| `USER32` | `MessageBoxA` is imported. Headless normal operation does not justify deleting its dependency; engine errors must not hang indefinitely in an invisible dialog. |
| `ole32` | `CoTaskMemAlloc` and transitive COM/runtime imports. |
| `WS2_32`, `ADVAPI32` | Socket operations and `GetUserNameA`; imports alone do not show whether the network/live-edit path is used in ordinary generation. |

The initial candidate needs:

1. Native Bionic ARM64 Wine loader, wineserver, Unix `ntdll` and the actual recursive ELF dependency closure, with `/system/bin/linker64` compatibility and no glibc dependency.
2. Wine's ARM64EC/ARM64X PE implementations of the imported system DLLs, API-set support, NLS/configuration files and a clean private prefix. Use one consistent Wine build rather than mixing Wine9 builtin DLLs with Wine11 Unix code.
3. A provenance-pinned `libarm64ecfex.dll` built with the ARM64EC toolchain and its runtime imports. FEXCore is compiled into this PE module; a Linux `FEXInterpreter` executable/rootfs is not required by this architecture.
4. The unchanged x64 worker, owner DLL and owner procedure/resource files.
5. A Bionic FEX UnixLib companion when enabling its host helpers, shared profiling data or file-mapping cache path. It is **not proven mandatory for initial execution**: the inspected FEX PE code has explicit missing-companion fallbacks. The unmodified companion build uses `-lrt` and POSIX `shm_open`, so Linux-generated `.so` files cannot simply be assumed Android-compatible. Its Bionic build should use an audited private-file-backed shared-memory adaptation and the Android NDK. [FEX PE build](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/Source/Windows/ARM64EC/CMakeLists.txt), [UnixLib build](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/Source/Windows/UnixLib/CMakeLists.txt), [UnixLib host implementation](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/Source/Windows/UnixLib/FEXUnixLib.cpp)

The public Wine archive's size is not the minimum runtime size. Its configure script enables desktop audio, fonts, X11, graphics and media features. A headless source build can disable unnecessary backends, but retain the import closure and only prune after successful replay. DXVK, VKD3D, Mesa/Turnip, an X server, OpenXR translation, desktop audio and Steam client services are not requirements of our CPU worker design. They should not be bundled merely because the general-purpose launcher uses them. Unity continues to own rendering, Quest XR, video, audio and gameplay; approved EOS multiplayer remains outside this worker. [Android ARM64EC build configuration](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/build-scripts/build-step-arm64ec.sh)

## Android launch and memory issues to resolve

**Executable placement.** The Quest app currently targets SDK30. Android29+ prohibits direct execution of files inside writable app home storage. Package native ELF executables and libraries under APK `lib/arm64-v8a`, extract them into `nativeLibraryDir`, and launch there. Use Android-compatible `lib*.so` package names and explicit loader mappings instead of expecting Wine's desktop directory layout. Writable private storage remains suitable for prefix, sockets, cache and copied interpreted data, subject to the actual mapping policy. [Android execution restrictions](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission)

GameNative's modern flavors target SDK36; its `ProcessHelper` prefixes launches with `/system/bin/linker64`. Its Bionic launcher also preloads redirect shims and points nested launches back to its Wine path. These choices prove that its APK launch behavior is part of the stack, not that copying a WCP archive will work in ours. Our packaged launchers must independently cover `exec_wineserver`, `CreateProcessW`, Wine re-execution and child environment inheritance. Stdout remains exclusively GHPR protocol; Wine/FEX diagnostics go to stderr. [GameNative flavors](https://github.com/utkarshdalal/GameNative/blob/7074d14d806a5595d26bbbf6d067ac1a665eb853/app/build.gradle.kts), [process helper](https://github.com/utkarshdalal/GameNative/blob/7074d14d806a5595d26bbbf6d067ac1a665eb853/app/src/main/java/com/winlator/core/ProcessHelper.java), [Bionic launcher](https://github.com/utkarshdalal/GameNative/blob/7074d14d806a5595d26bbbf6d067ac1a665eb853/app/src/main/java/com/winlator/xenvironment/components/BionicProgramLauncherComponent.java)

**Source fixes required for our layout.** Wine's small ELF loader locates `ntdll.so` relative to its own path. Its Unix loader normally searches for a sibling `wineserver` before the `WINESERVER` override. Packaging renamed native binaries therefore needs explicit, bounded path adaptations. GameNative's Android prefix patch hardcodes `Z:` to `/data/data/app.gamenative/files/imagefs/`; the existing GHPR bridge uses absolute original inputs via `Z:`. Initialize our own prefix with a correct root mapping, or replace that patch. Its Android client already places server sockets under `WINEPREFIX/.wineserver`, potentially eliminating the current Wine9 `/tmp` binary relocation; inspect matching server code before relying on that. [ELF loader](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/loader/main.c), [Unix loader](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/dlls/ntdll/unix/loader.c), [Android prefix patch](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/android/patches/common/dlls_ntdll_unix_server_c.patch), [Android client socket path](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/dlls/ntdll/unix/server.c)

**Native and translated executable mappings.** GameNative's ARM64EC patch copies PE image data into anonymous mappings to avoid file-backed executable restrictions after relocation. This addresses a real Android issue, but its explanatory comment does not prove that every Quest OS SELinux policy permits Wine/FEX JIT mappings. Verify anonymous executable mappings, transitions, signal handling and seccomp in an installed target30 application, not only `adb shell`, `run-as`, Linux QEMU or root. No SELinux disabling, rooting, SDK downgrade or proprietary shim should be part of the proposed solution. [Anonymous PE mapping patch](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/android/patches/arm64ec/dlls_ntdll_unix_virtual_c.patch)

**Synchronization.** Do not assume `/dev/ntsync` or optional kernel interfaces exist on Quest. First establish correctness with Wine server synchronization; then compare the release's userspace ntsync fallback and fsync where permitted. `PROTON_NO_NTSYNC=1` disables ntsync, while `PROTON_NO_KERNEL_NTSYNC=1` selects userspace ntsync; these controls do not independently describe every other Wine synchronization backend. The userspace library needs the same private `TMPDIR`/`NTSYNC_SHM` across clients/server. Leave its optional spin count at zero until actual wait measurements justify another value. [ntsync source documentation](https://github.com/GameNative/ntsync-android/blob/7ce6435e5979b1cb5341aa4b299f31e8937fe121/README.md)

**Mixed-mode memory.** Wine's `WINEVMEMMAXSIZE` patch rejects individual virtual allocations above a configured MiB size; it does not cap total committed memory or process RSS. Measure reservations separately from committed/RSS/PSS pages. Account for engine heap, Wine/server mappings, FEX code/cache and thread state, Unity assets, and transient socket-buffer copies. The inspected FEX ARM64EC source allocates a 256 KiB emulator stack per initialized thread in addition to guest thread stacks. A generous virtual reservation can be harmless; a similarly sized resident allocation can evict game assets or trigger Android termination. Do not substitute an unexplained cap for measurement.

**CPU ordering and numerical equivalence.** ARM64EC retains x64-compatible addresses/data layout but not x86 hardware ordering. FEX supplies memory-ordering/atomic emulation. Preserve conservative correctness settings, actual host-feature detection and full x87 precision before experiments with faster options; never force SVE or disable ordering merely because a gaming preset does so. The engine imports C++ synchronization and performs floating-point procedural generation, making thread ordering, exception behavior and geometry output genuine compatibility requirements. [Official FEX memory-model implementation notes](https://github.com/FEX-Emu/FEX/blob/7d3090f78237267b2adf2d32116f0105b8d665cb/FEXCore/docs/MemoryModelEmulation.md)

## Concrete next experiment

1. **Reproducible inventory before execution.** Pin one Wine source/release and one FEX source/build, Android NDK/toolchain revisions, licenses, patches and every artifact hash. The inspected Wine workflow uses NDK r27d (`27.3.13750724`) plus ARM64EC-capable LLVM MinGW `20250920`; Unity's Android NDK alone does not build ARM64EC PE libraries. Resolve the unknown FEX2609 provenance or build FEX from an explicit compatible source revision. Audit every packaged ELF interpreter, architecture, `DT_NEEDED`, runtime search path, page alignment and every PE import/CHPE metadata field. Reject hardcoded `com.termux`/`app.gamenative` executable dependencies. [Pinned Wine build workflow](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/.github/workflows/build-proton.yml)
2. **Small installed native probe APK.** Use a disposable NDK/Gradle harness with the same minimum/target SDK and extraction policy as the port. Launch the packaged native Wine/server from an ordinary app process. Run the unchanged x64 worker initially with a small test DLL that exercises threads, TLS, heap ownership, mutex/event waits, floating-point/by-value calls, exceptions/unwind and callbacks. Preserve GHPR framing and stderr separation. Record executable mapping/sandbox failures with useful diagnostics and bounded timeouts; include one nested child-process test. This avoids a Unity import, shader audit or full game rebuild for a loader failure.
3. **Original engine equivalence through the same socket.** Replace the test DLL with the owner's unmodified Apparance DLL and read-only original procedures. Replay the existing Scenario001 oracle through all twelve exports. Existing reference evidence has 18 native builds, 87 resource requests and 18 canonical task streams totaling 56,133 bytes; the bridge proof additionally covers reentrant callbacks, task/string lifetimes and shutdown/restart. Require the same strict comparison of geometry, materials, parameters and task bytes, allowing only the existing scheduling-derived handle canonicalization. Add recorded Guildmaster seed/resource journals and several restarts; one fixed campaign scenario is insufficient for restored dynamic Guildmaster scope. Save tests use disposable procedure copies. [Existing replay](../tools/quest-procedural-runtime/replay.py), [bridge proof](../tools/quest-procedural-runtime/bridge_proof.py)
4. **Paired Quest performance experiment.** Compare corrected Box64/Wine and ARM64EC Wine/FEX with the identical owner inputs, seeds, synthesizer count, heap budget and generated-task checksums. Record cold and warm prefix start, engine initialization, first/last build task, resource replies, total generation, user/system CPU time, peak RSS/PSS and thread count. Repeat after sustained use to expose thermal/scheduling effects; retain the native PC reference as a correctness/timing context, not a hardware speed prediction.
5. **VR contention test only after native success.** Integrate the alternate launcher behind the unchanged bridge for a focused headset run. Measure Unity CPU/GPU frame times, missed frames and memory while entering campaign and Guildmaster maps, changing scenes and returning to menu. Observe idle generation too: the bridge's synchronous per-frame `ApparanceUpdate` and task polling remain possible VR costs regardless of translator. Do not announce a usable port because one ELF starts or one journal finishes.
6. **Choose from measured results.** Adopt FEX if it passes sandbox/protocol/geometry gates and provides useful time or memory gains without VR regressions. Retain the corrected Box64 option until that evidence exists. Cache versioned runtime initialization across launches; neither backend should trigger repeated minute-long content validation or hide menu startup behind unrelated generation. The requested few-second startup remains a product requirement, separate from the translator's loader proof.

## Licensing and remaining gaps

Wine's inspected `COPYING.LIB` is LGPL2.1, with per-file notices defining applicable options. FEX/FEXCore inspected license files are MIT. `ntsync-android` declares LGPL3.0-only in `Cargo.toml`; enabling its static integration into Wine artifacts needs corresponding source/build/relink obligations recorded in the distribution plan. GameNative application code is GPL3.0; reusing its launcher code also requires reviewing that license against our project, rather than assuming Wine's license covers the launcher. This plan proposes our narrow existing process boundary instead of copying the whole launcher. [Wine license](https://github.com/GameNative/proton-wine/blob/555aa70febb7d36e82d96697b554ff8f4fe0bb1a/COPYING.LIB), [FEX license](https://github.com/GameNative/FEX/blob/555e8bd2d1f07fc7455e21324c9f9c7303c7ee7d/LICENSE), [ntsync package license](https://github.com/GameNative/ntsync-android/blob/7ce6435e5979b1cb5341aa4b299f31e8937fe121/Cargo.toml), [GameNative license](https://github.com/utkarshdalal/GameNative/blob/7074d14d806a5595d26bbbf6d067ac1a665eb853/LICENSE)

GameNative's third-party notices explicitly describe `libredirect.so` as proprietary and source-withheld, including app-identifier and newer Android execution adaptations. Other bootstrap/GPU helpers are also source-withheld. Their presence in a GPL application is not permission to reuse those binaries; our design must be independently functional without them. Steam client/bootstrap/GPU helpers are outside this headless engine scope in any case. [GameNative component notices](https://github.com/utkarshdalal/GameNative/blob/7074d14d806a5595d26bbbf6d067ac1a665eb853/THIRD_PARTY_NOTICES)

Open gates are: exact compatible FEX artifact provenance; minimum Wine/PE/ELF closure; source-owned Android path/child-launch adaptations; Quest app-context JIT and synchronization behavior; original campaign and Guildmaster equivalence; and paired memory/loading/VR-frame measurements. None has been claimed as verified on hardware by this evaluation. The user's own engine/game data remain local builder inputs; no proprietary game assets or provider services are introduced by this route.
