## RAM, commit and smaller hosts

The capture has63.73GiB installed RAM,32.83GiB available physical RAM and24.50GiB
allocatable commit. Installed RAM is not additional allocation capacity.
Windows reports process allocation capacity separately from system commit
limit/usage; both are now recorded through typed Win32 calls. Current Python
working/private memory is also reported when available.

The previous policy subtracts another10% of total RAM from capacity that already
excludes current allocations. The reviewed policy instead reserves future Unity
growth6GiB and bounded transient capacity2GiB. The measured native worker reserve
remains32GiB (previous B625 Linux Release peak approximately26GiB); additional

Windows16/32GiB hosts may start exactly one paged native worker when enough
available commit is measured. Linux uses actual free swap within cgroup limits.
Additional native workers require physical headroom. `--jobs` cannot bypass the
capacity gate; paging speed and a complete build on smaller hosts are unverified.
The Builder never changes the user's paging-file or system settings.

A typed prerequisite check runs after original input qualification, before the

document. The Wizard presents measured installed/available RAM, commit and need,
with retry/diagnostics. This neutral prerequisite gives no fabricated work credit

Microsoft's [MEMORYSTATUSEX documentation](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)

provides system commit limit/usage. Automatic paging-file growth is not assumed.
