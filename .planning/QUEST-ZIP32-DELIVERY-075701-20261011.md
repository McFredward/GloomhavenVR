# Large Android Player delivery and targeted final repair — 2026-10-11

## Evidence and cause

`quest-build-support-20261011T075701Z-ec02255f.zip` identifies the preceding
Builder `e740fcdbd`, new-build Runtime668. Its existing Player remains the
successfully compiled Runtime665 under its original input/provenance. The
current run reaches `finish-build` and fails in zipalign after approximately
4.8 seconds, without source/asset preparation or another Unity invocation.
The missing tool message was supplied separately by the maintainer:
`Unable to open ...GloomhavenVR-Quest.capable.apk... as zip archive`.

The original Unity Player uses ZIP32. CPython's conservative ZIP64 threshold
is 2 GiB, below ZIP32's actual unsigned limits. The previous raw-entry copier
therefore introduced ZIP64 central records when rewriting a larger ZIP32
Player. The pinned Android30.0.2 zipalign rejects that rewritten archive.
The same native failure was reproduced using a retained real 2.7-GiB Player.

## Repair and retained work

The APK-specific writer preserves ZIP32 central records, original compressed
payloads, supported metadata and comments. It validates the actual unsigned
size/offset/count limits; it does not alter Python's process-global ZIP policy.
Alignment, signing, signature verification and atomic publication remain
required. An unsuccessful rewrite preserves the original compiled APK and any
previously published result. No original game import or Unity rebuild is needed.

Update capability/signing, APK validation, delivered Shader validation and
delivered Compute validation now have independent completed receipts. A retry
reuses byte-qualified successful owners and reruns only an invalid or incomplete
owner. A corrupt derived audit JSON regenerates its own audit; changed selected
materials or frozen audit consumers invalidate their corresponding owner.
Malformed derived certificate evidence is recreated after actual native
certificate verification; a valid different identity remains refused and
the private key/password files are never replaced.
Actual APK/bank byte identities use existing strong change-stamp witnesses;
filesystems without a reliable change witness still verify bytes.

These receipts never relabel the existing665 Player as668. Original native
payloads, game identity, the private signing key and required delivery gates
remain authoritative. This repair does not promise automatic recovery from an
unavailable original file or an unknown invalid native program. The existing
targeted source/import repair owners continue to handle their proven contracts.

The first delivered Shader audit reports actual root/bundle counts. Final
delivery reaches100 only after its checks and result publication finish.
Support exports prioritize the current failed tool log while retaining their
existing file/size/redaction limits. The Wizard surfaces the native explanation
and the retained completed Player instead of hiding it behind a Python exit.
