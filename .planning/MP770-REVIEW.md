# Results responsiveness review

The paired Build769 hardware logs establish that both peers now accept the full
common Results picture. The maintainer confirms identical content and clarifies
that only the guest sees its own scroll late; the host sees that guest's action
promptly. These Info logs do not time individual scroll requests. Do not present
the reported two-to-three-second delay as an automated packet measurement.

## Visible scrolling

Accepted small scroll state previously moved the hidden native guest components.
The visible inert Results copy waited for its larger presentation snapshot. The
new projector maps exact native identity paths to the validated common copy and
uses that copy's viewport/content geometry. It does not import private guest row
heights, predict input or add callbacks to an inert clone. Projection runs between
snapshots and after the existing graph paint, before its descriptor-cache return.
Thus a delayed graph cannot restore an older visible scroll position. Linked
handles use the same accepted content value, retaining source size/direction;
standalone bars retain their own ordered state.

Original author execution, permission checks, per-opening generation, input
sequencing, simultaneous opposite input ordering and native continuation remain
unchanged. The focused real Unity fixture checks the actual visible clone and
rendered pixels, rather than only its hidden ScrollRect.

## Shared frame motion

The producer previously embedded changing frame poses in reliable fragmented
picture traffic. The existing pose-only Results grammar now uses a dedicated,
bounded native unreliable side action, like existing rig motion. Native send
flags are restored even on failure. Full content, dependencies and close remain
on their original reliable path; no global scheduler or wire grammar changes.

Separate incoming queues and watermarks keep fast motion from replacing a pending
full picture or suppressing its sparse dependency. Only an original author's full
picture establishes an opening. Pending motion is applied after that bootstrap.
Per-sender pose revisions prevent a delayed full picture from rewinding a newer
accepted pose while still allowing its content to paint. Existing common move
claims, local grip priority, independent zoom/reference metric and the established
SharedWindowPoseTrack interpolation remain authoritative. Close/reopen, native
episode retirement and peer forgetting revoke old targets. Stationary loss repair
uses the existing bounded half-second heartbeat; no catch-up burst is introduced.

An independent read-only review of the motion changes found no concrete blocker.
Vanilla clients retain the existing ignored sentinel path; no new gameplay RPC,
automatic confirmation, native controller or callback is introduced.

## Final compiled boundary and evidence limits

The strict final-union DLL comparison with the preserved Build769 DLL changes four
behavior types: FfsNetTransport, NetAvatarDriver, ScenarioResultsPose and
SharedWindowScrollCoordinator. The only added type is SharedWindowScrollPicture.
Eight other changes are inlined ModBuild stamps. All 32 embedded resources are
byte-identical; no types were removed. All 672 config keys, 289 Harmony patches
and 4,862 log tokens are unchanged. Native Results controllers, picture sampling,
original animation/audio, footer geometry and continuation actions are untouched.

This is Class B, with the maintainer's explicit affected-tests-only instruction.
Reuse the qualified Build769 aggregate checkpoint for unchanged consumers, assets,
wire goldens and unrelated suites. Its original complete invocation remains a
recorded failure due to 15 private-ADB startup refusals; those refused scopes were
individually repaired and passed. This round does not claim a fresh complete gate.

The scroll fixture uses actual Unity UI/visible pixels but a coordinator mailbox.
Motion tests execute production producer/codec/ingress and pose/track kernels with
declared native socket, timing and placement ports. Neither proves Photon Internet
latency or perceived HMD smoothness. Those remain the next paired hardware check;
the delivery removes the demonstrated content-packet dependency without claiming
an unmeasured end-to-end latency guarantee.
